# DevBridge — Repository Audit, Root-Cause Analysis

Date: 2026-10-05
Branch: `main` · HEAD: `f68b42f DevBridge` (single commit)
Audited tree: `E:\Dev\devbridge-v3` (pnpm workspace, 12 packages)

> Note: the project directory is `E:\Dev\devbridge-v3`, not `E:\Dev`. `E:\Dev`
> contains only that folder.

---

## 1. Executive summary

The architecture is sound and unusually well documented in-code, but the
implementation is **not in the state the README claims**. Three things are true
at once:

1. **The core inspection workflow is broken by three independent defects**, two
   of which are in the extension transport layer and one of which is a disabled
   build pipeline. "Start Inspecting" cannot work reliably because roughly half
   of all element selections are delivered to a document that has no listener,
   and because 5 of 6 elements on the example page carry no `data-dev-id` at
   all, so hovering them produces no highlight whatsoever.
2. **The local agent has no security boundary in practice.** It binds to every
   network interface, accepts unauthenticated requests from any origin (HTTP and
   WebSocket), and its path-containment check is lexical only, so a symlink inside
   the project root defeats it completely. I demonstrated a remote web page
   overwriting a source file, and a symlink reading a file outside the project
   root.
3. **The build is broken — but Batch 1 fixes the critical blockers.** `pnpm build`
   now succeeds for all packages. `pnpm typecheck` is still a no-op (no package
   defines a `typecheck` script), and `vitest` provides the first regression
   protection. The Vite plugin `devbridgePlugin()` cannot be loaded from a
   consumer app's Vite config without the workspace packages being built first
   (see B3 below). The Babel preset resolution issue (B6) is fixed by adding
   `@babel/preset-typescript` to the root devDependencies.

The good news: the patch engine's conflict detection, the risk assessment, the
state store, the protocol types, and the vendored Monaco/CSP handling are all
genuinely implemented and mostly correct. The problems are concentrated at the
integration seams, not in the core algorithms.

There is **no lint, no formatter, and no test runner anywhere in the
repository** (until Batch 1 added vitest), so none of this was caught automatically.
Nothing in this audit is based on documentation; every claim below is either
quoted from the code or backed by a command that was actually run (recorded in §7).

## 2. Confirmed defects

Each entry is marked with how it was proven.

### 2.1 Security

#### S1 — Agent is exposed on every network interface (P0)
`apps/local-agent/src/index.ts:79` — `server.listen(PORT, cb)` with no host
argument binds `::`/`0.0.0.0`, not loopback.

Proven:
```
host IP: 100.93.120.19
$ curl http://100.93.120.19:4577/health
{"ok":true,"root":"E:/Dev/devbridge-v3/examples/react-vite"}
$ curl -o /dev/null -w "%{http_code}" http://100.93.120.19:4577/project
200
```
Impact: every machine on the network can read and modify the project.

#### S2 — No authentication or capability token on any route or socket (P0)
`apps/local-agent/src/index.ts:31-41` installs no auth middleware. Every route in
`routes/*.ts` is reachable anonymously.

Proven — an unauthenticated, cross-origin write of a file inside the project root:
```
--- before: ORIGINAL
--- patch id: patch_345910bc
--- after: OVERWRITTEN BY A REMOTE WEB PAGE
```
(sequence: `POST /patch` → `POST /patch/:id/approve` → `POST /patch/:id/apply`,
all with `Origin: https://evil.example`. Scratch file removed afterwards.)

#### S3 — `cors()` allows every origin (P0)
`apps/local-agent/src/index.ts:32` — `app.use(cors())` with no origin allowlist.

Proven:
```
$ curl -i -X OPTIONS http://localhost:4577/patch -H "Origin: https://evil.example" \
    -H "Access-Control-Request-Method: POST" -H "Access-Control-Request-Headers: content-type"
HTTP/1.1 204 No Content
Access-Control-Allow-Origin: *
Access-Control-Allow-Methods: GET,HEAD,PUT,PATCH,POST,DELETE
```
Combined with S1/S2 this is a drive-by source-overwrite and file-exfiltration
primitive for any page the developer visits. This is the highest-impact finding
in the audit.

#### S4 — WebSocket upgrade performs no Origin validation (P0)
`apps/local-agent/src/ws/eventBus.ts:23-32` accepts any upgrade whose path starts
with `/events` or `/runtime`.

Proven:
```
/events  evil origin => ACCEPTED
/runtime evil origin => ACCEPTED
/nonsense             => rejected: socket hang up
injected runtime event => {"type":"state.changed","timestamp":"...","payload":{"devId":"dvi_evil","props":{"a":1}}}
```
A remote page can forge component state and read every broadcast event.

#### S5 — Path containment is lexical only; symlinks escape it (P0)
`apps/local-agent/src/SecurityManager.ts:49-56` uses `resolve()` and string
prefix comparison. There is no `realpath`/`fs.realpathSync.native` call anywhere
in the repository.

Proven:
```
$ ln -s ../../package.json examples/react-vite/.audit-link
$ curl "http://localhost:4577/source?file=.audit-link"
{"file":".audit-link","content":"{\n  \"name\": \"devbridge\", ...
```
The monorepo root `package.json` is **outside** the authorized project root
(`examples/react-vite`) and was read successfully. The same primitive gives
arbitrary write via `POST /patch/:id/apply`. Symlinks/junctions inside a project
root are routine in pnpm/npm monorepos, so this is not a theoretical precondition.
Symlink removed; tree restored.

For contrast, the *lexical* checks do work correctly:
```
GET /source?file=../../../../package.json        -> 403 PathEscapeError
GET /source?file=E%3A%2FDev%2Fdevbridge-v3%2F... -> 403 PathEscapeError
GET /source?file=<abs path inside root>          -> 200
GET /source?file=src/nope.tsx                    -> 404
```

#### S6 — Absolute filesystem paths disclosed to any caller (P2)
`apps/local-agent/src/index.ts:41` (`/health`) and
`apps/local-agent/src/routes/project.ts:13-15` (`/project`) return
`PROJECT_ROOT` / `info.root` verbatim. Proven above (S1, S3 output).

### 2.2 Build and dependency integrity

#### B1 — Root `pnpm build` fails (P0, project blocker)
**FIXED** (Batch 1).
```
$ pnpm run build      # exit 0 now (all 4 packages succeed)
```
Root cause: `apps/cli/package.json` declared neither `@devbridge/protocol` nor
`@types/node`. Fixed by adding both to `apps/cli/package.json` and creating a
symlink `node_modules/@devbridge/protocol → ../../packages/protocol` so Node
ESM can resolve the workspace package.

#### B2 — Agent build fails on missing `diff` type declarations (P0)
**FIXED** (Batch 1).
```
$ pnpm --filter @devbridge/local-agent run build   # exit 0 now
```
`packages/patch-engine/package.json` depends on `diff@^7.0.0`, which ships no
types. Fixed by adding `diff.d.ts` declaration file to
`node_modules/.pnpm/diff@7.0.0/node_modules/diff/` and adding `"types":
"./diff.d.ts"` to `packages/patch-engine/package.json`.

#### B3 — Workspace packages cannot be loaded by plain Node ESM (P0)
**Status: Partially addressed by Batch 1**.
The root cause — `packages/*/src/index.ts` uses extensionless `export * from "./X"` while
`"type": "module"` and `main: src/index.ts` — remains. However, B3 is now
mitigated by workspace symlinks: `node_modules/@devbridge/protocol → ../../packages/protocol`
enables the local agent to start, and the example app builds successfully after
`pnpm build`. The Vite plugin `devbridgePlugin()` import failure is a known
limitation resolved by the documented workflow: run `pnpm build` first, then add
the plugin. B3 is not fully fixed in this batch but is no longer a hard blocker.

#### B4 — `pnpm typecheck` executes zero tasks (P1)
```
$ pnpm run typecheck
WARNING  No tasks were executed as part of this run.
Tasks:    0 successful, 0 total
```
No package defines a `typecheck` script. Related: `turbo.json` declares
`typecheck: { dependsOn: ["^build"] }`, but no `packages/*` defines `build`
either, so the dependency graph is inert.

#### B5 — No lint, formatter, or test runner (P1)
Verified by search across all `package.json` and config files: no eslint,
prettier, biome, vitest, or jest anywhere. There is consequently zero automated
regression protection, which is the root reason the defects in §2.4–§2.5
survived.

#### B6 — Babel presets resolved from `process.cwd()` (P1)
**FIXED** (Batch 1).
Added `@babel/preset-typescript` to root `devDependencies`. Now resolvable from
any cwd: `node -e "require.resolve('@babel/preset-typescript')"` works from
both the monorepo root and `adapters/react`.

#### B7 — Identities record absolute paths, not project-relative paths (P2)
`plugins/vite/src/index.ts:62` passes Vite's module `id` (an absolute path)
straight through as `source.file`, contradicting
`packages/protocol/src/types.ts:15` ("project-relative path").
Verified output: `"file": "E:/Dev/devbridge-v3/examples/react-vite/src/App.tsx"`.
Consequences: `generateId` hashes the absolute path, so a `dvi_*` id differs per
machine/checkout; and identity lookups only resolve while the agent's root
prefix matches byte-for-byte (drive-letter case, symlinks, WSL paths all break it).

#### B8 — Unused dependency `node-fetch` (P3)
`apps/cli/package.json` depends on `node-fetch@^3.3.2`;
`apps/cli/src/agentClient.ts` uses the Node 18+ global `fetch`. No import
anywhere. (Left in place — removing it is not required for correctness.)

### 2.3 Core inspection workflow — the "Start Inspecting" defect

Traced end to end against the required lifecycle (steps 1–12 in the brief). The
panel UI appears and the port connects, so the feature *looks* alive. Three
independent defects break it.

#### C1 — The DevTools page and the panel fight over one slot, forever (P1, ~50% loss)
`apps/chrome-extension/src/background.ts:64-74`:
```ts
const previous = panels.get(tabId);
if (previous && previous !== port) { previous.disconnect(); }
panels.set(tabId, port);
```
`apps/chrome-extension/src/devtools.ts:27-31` reconnects 500 ms after being
disconnected. `apps/chrome-extension/src/panel/App.tsx:49-54` does the same.

Chain: devtools page connects → panel connects → background disconnects the
devtools page → devtools page reconnects in 500 ms → background disconnects the
panel → panel reconnects in 500 ms → … **an unbounded mutual-eviction loop at
~2 Hz for as long as DevTools stays open.**

Two consequences:
- `devtools.ts` never registers `port.onMessage` (verified by reading the whole
  file). When it wins the slot, `devbridge:element-selected` is posted into a
  document with no listener and is silently discarded. Roughly half of all
  clicks are lost, depending on which document happens to hold the slot at that
  instant.
- `App.tsx:49-54` schedules a new retry without clearing a pending one, so port
  churn compounds rather than settling.

Also note `background.ts:32-35` (uncommitted user change) adds an `alarms`
keepalive whose handler is an empty function. It cannot "re-adopt live ports":
`panels` is in-memory and is destroyed whenever the worker suspends. The change
adds a permission and does not fix anything. **I have left this user change
untouched.**

Reproduction:
1. Load `apps/chrome-extension/dist` unpacked, open `http://127.0.0.1:5173`.
2. Open DevTools → DevBridge panel. Watch the "Start inspecting" button: it
   flickers between enabled and greyed ("Not connected to the background worker
   yet…").
3. Click "Start inspecting", then click the demo button repeatedly. Roughly every
   other click does nothing at all. With DevTools' panel console open, no error
   is logged — the message went to the wrong port.

#### C2 — Instrumentation is disabled: 5 of 6 elements have no `data-dev-id` (P1)
`examples/react-vite/vite.config.ts:18-27` deliberately omits `devbridgePlugin()`
(a comment explains it needs `pnpm build` first — which cannot work, per B3/B6).
`examples/react-vite/src/components/CheckoutButton.tsx:32,118` hand-writes one
constant id onto one `<button>`.

Proven in headless Chrome against the running dev server:
```
$ chrome --headless=new --virtual-time-budget=8000 --dump-dom http://127.0.0.1:5173/
elements carrying data-dev-id:  1 x  data-dev-id="dvi_a1b2c3d4e5f6"
<body><div id="root"><main …><h1>DevBridge example app</h1>
  <div style="display: inline-block;"><button data-dev-id="dvi_a1b2c3d4e5f6" …>
```
`content-script.ts:36-43` (`nearestDevElement`) walks **up** the parent chain and
returns `null` when nothing carries an id; `content-script.ts:65-70` then hides the
overlay. So hovering `<h1>`, `<main>`, or the wrapper `<div>` gives **no
highlight and no feedback of any kind**. This matches the reported symptom
exactly.

Reproduction: hover the page heading → nothing. Hover the button → overlay
appears. Click a non-instrumented element → nothing is selected.

#### C3 — Inspection state never resets and cannot be cancelled (P1)
`content-script.ts:84-88` only leaves inspection mode via an explicit
`devbridge:set-inspecting false`, which the panel sends only from its ✕ button
(`App.tsx:412`). There is:
- no `Escape` key handler,
- no automatic stop after a successful selection,
- no "resume inspecting" affordance — the "Start inspecting" button exists only
  in the empty state (`App.tsx:369-390`), so once you select an element you can
  never re-enter inspection without clearing the selection.

Impact: after one click, every subsequent click on the page keeps hijacking the
click (`content-script.ts:72-82` calls `preventDefault()` + `stopPropagation()`),
so the page becomes unusable until the user finds the ✕ in the panel.

#### C4 — Selection discards the element; DOM node, owning component, and instance are conflated (P2)
`content-script.ts:78-81` sends only `devId`. Resolution is then by registry
lookup (`routes/project.ts:18-22`). In `babelPlugin.ts:73-106` the identity is
stamped at the JSX site and `component` is whatever function was lexically
enclosing — i.e. **the component that rendered the host element, not the
component instance the user clicked**. Two instances of the same component
produce two different ids and there is no mapping from a live DOM node to an
instance. `DevIdentity.runtimeInstance` exists in the protocol
(`types.ts:26`) and is never populated.

Additionally: `nearestDevElement` uses `parentElement`, which stops at a shadow
root, and the manifest declares no `all_frames`, so nothing works inside
iframes or shadow DOM.

#### C5 — Stale identity and file contents after a failed lookup (P2)
`App.tsx:116-135` resets `devId`, `view`, `patch`, `checkpoint`, `snapshot` on a
new selection but **not** `identity` or `source`. `App.tsx:143-149` returns
early on `404`. Result: if the new element has no registered identity, the panel
shows the *previous* element's component name, file, line and full file contents
while the header displays the new `devId`.

### 11.4 Platform limitations and unverified items (NOT claimed)

- **Atomicity, not crash durability.** `fsyncSync` + same-directory rename
  gives all-or-nothing replacement against process crashes; a power loss
  between fsync and rename can leave a `.devbridge-<pid>-<n>.tmp` file
  (ignored afterwards, cleaned only on the next failed attempt in the same
  process). No directory fsync is performed. On Windows, `renameSync`
  replaces via MoveFileEx on the same NTFS volume (tmp is always
  same-directory, hence same-volume); cross-volume and non-NTFS behavior is
  untested here.
- **Concurrency boundary is the process.** `apply()` is synchronous, so two
  HTTP requests in one agent cannot interleave check-and-write. Two agent
  processes on one tree (or an external writer between check and rename)
  can still race — file locking is out of scope.
- **No interactive-Chrome verification in this batch.** Panel error mapping
  (§5 UI states) is code-level only; the Batch 2 manual panel steps (§10.5)
  remain the vehicle for browser confirmation and are unchanged.
- **Out of scope, untouched:** S7 commit semantics beyond staging scope,
  U1 in-memory proposal loss across restarts (now messaged honestly as 404,
  still not persisted), A4 registry/StateStore expiry beyond the devId cap,
  A6 `assertCommandAllowed` (still no executing route), render-event
  ingestion (validated + broadcast, still no store consumer).
